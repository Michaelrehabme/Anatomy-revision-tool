# Native wrapper trial (Capacitor, Android)

4 October 2026. Roadmap card: "Try a native wrapper with review reminders".

**Status: half done.** The parts that need no phone are built. No APK exists, because this
machine has no Android SDK. Nothing here has run on a device, so every statement below about
what happens inside the shell is from documentation, not from observation, unless it says
"tested".

**About the quotes.** The documentation and policy pages were fetched on 4 October 2026. The
fetch tool passes pages through a summariser, so short quotes should be exact but have not been
compared character by character with the source. Before relying on any of them for a store
submission, open the link and read the line. Anything marked *(from memory)* was not fetched.

the plugin chunk is never fetched. Entry chunk after the change: 1,903.96 kB (it was 1,903.01 kB;
the ceiling is 2 MiB, 2,097 kB). The plugin is in its own 9.7 kB chunk.

### How the reminder decides

- "Due" is not redefined. The count comes from `buildReviewQueue` (`lib/reviewQueue.ts`), the
  function behind the Today screen's due count, asked about the reminder time instead of now.
- One notification, at 18:00 local time, on the first day (within 14) by which at least one
  review is due. Text: "12 reviews are due." / "1 review is due."
- It is cancelled and set again every time the Today screen loads, so finishing today's reviews
  moves it to the next day that has any.
- Locked areas never count.
- Permission is requested the first time there is something to remind about, not at launch. A
  refusal is respected and not asked again.

**Decisions in that list that are yours:** the hour (18:00), one a day, and no in-app switch to
turn reminders off. A store build needs that switch.

## How to run it on a phone

1. Install Android Studio (Otter 2025.2.1 or newer). In its SDK Manager install **Android 16
   (API 36)** and the platform tools.
2. Use a checkout with a real `npm ci`, not a junctioned `node_modules`.
3. Choose the build:
   - **No account, no Firebase** (safest first run): no `.env`, so the app runs on local
     storage. Good for testing offline, the service worker and the notification.
   - **Real accounts**: copy `.env` in. Expect Google sign-in to fail (see below); email and
     password should work *(from memory, untested)*.
4. `npm run native:sync`
5. `npx cap open android`, wait for Gradle to finish, plug the phone in with USB debugging on,
   press Run. Or, without the IDE: `cd android && gradlew.bat assembleDebug`, then
   `adb install app\build\outputs\apk\debug\app-debug.apk`.
6. Check, in this order, and write down what happens:
   1. The app opens to onboarding or Today, and pictures load.
   2. Aeroplane mode, force-stop, reopen. It should still open: the files are inside the APK.
   3. In Chrome on the desktop, `chrome://inspect` → the WebView → Application → Service
      Workers. Is one registered? Cache Storage: do `locusmsk-anatomy-images-*` entries appear
      as pictures are viewed?
   4. Answer a few questions and return to Today. Android should ask for notification
      permission. Allow it.
   5. To see the notification without waiting for 18:00: set the phone's clock to 17:58, open
      the app, go to Today, wait.
   6. Finish every due review, return to Today, and confirm no notification arrives at 18:00
      that day.
   7. Reboot the phone before the reminder time. Does it still arrive? (The plugin declares
      `RECEIVE_BOOT_COMPLETED` for this.)

## How the PWA behaves inside the shell

### Service worker

- **Android: should register.** The shell serves the app from `https://localhost`, a secure
  origin. Capacitor: "It is recommended to keep this as `localhost` as it allows the use of Web
  APIs that would otherwise require a secure context" ([config](https://capacitorjs.com/docs/config)).
  Since Capacitor 7, `android.resolveServiceWorkerRequests` (default true) makes "service worker
  requests go through Capacitor bridge" (same page).
- **iOS: does not register by default.** The iOS scheme is `capacitor://`, and
  `serviceWorker.register()` fails with "must be called with a script URL whose protocol is
  either HTTP or HTTPS" ([capacitor#7069](https://github.com/ionic-team/capacitor/issues/7069),
  closed as not planned). The workaround is serving from a real https origin with App-Bound
  Domains ([WebKit](https://webkit.org/blog/10882/app-bound-domains/)); not verified.
- **The precache is redundant in the shell.** The app's files are already in the APK. The
  service worker's only remaining jobs are the runtime image cache and the "new version"
  prompt, and the prompt is wrong there: a new version arrives as a new APK, not a new worker.
- Capacitor's own PWA page does not say whether service workers run in the shells
  ([link](https://capacitorjs.com/docs/web/progressive-web-apps)).

### Offline area downloads (`src/features/pwa/offline/`, branch `worktree-agent-aafde415b98a1be1c`)

**This is the first real problem.** `dist/` is **327 MB**, nearly all of it pictures, and
`cap sync` copies all of it into the APK. So:

- As built, the APK carries every picture. Every area is "offline" from install and the
  download feature has nothing to do. The APK is about 327 MB before compression.
- Play has size limits on what an install can carry *(from memory: not fetched, check before
  planning around it)*. A 327 MB app is also a poor first download for a student on mobile data.
- The alternative is to leave `/anatomy/` out of the APK and fetch pictures from the live site.
  Then the download feature matters again, but its requests are relative (`/anatomy/...`), which
  inside the shell means `https://localhost` and a 404. They would need absolute URLs to the
  live site, and the site would need to allow that origin (CORS). That is real work in the
  offline code, and it is not started.
- Storage can be evicted. Capacitor: "The OS will reclaim local storage from Web Views if a
  device is running low on space. The same can be said for IndexedDB at least on iOS (on
  Android, the persisted storage API is available to mark IndexedDB as persisted)"
  ([storage guide](https://capacitorjs.com/docs/guides/storage)). The offline code already
  keeps its record inside the cache it describes, so an evicted area reads as not downloaded
  rather than as a broken one. I found no Capacitor statement about Cache Storage specifically.

### Firebase Auth

- **Google sign-in will not work as written.** The app uses `signInWithPopup`
  (`data/firebase.ts`). Google's policy: "A developer must not direct a Google OAuth 2.0
  authorization request to an embedded user-agent under the developer's control"
  ([OAuth policies](https://developers.google.com/identity/protocols/oauth2/policies), last
  modified 5 Aug 2026). The error is `disallowed_useragent`
  ([native apps](https://developers.google.com/identity/protocols/oauth2/native-app)).
- **The fix is a native sign-in plus `signInWithCredential`.** The usual plugin is
  `@capacitor-firebase/authentication` with `skipNativeAuth: true` ("Only needed if you want to
  use the Firebase JavaScript SDK"), then `GoogleAuthProvider.credential(idToken)` into the
  existing web SDK, so Firestore and the rules are untouched
  ([README](https://github.com/capawesome-team/capacitor-firebase/blob/main/packages/authentication/README.md),
  [JS SDK guide](https://github.com/capawesome-team/capacitor-firebase/blob/main/packages/authentication/docs/firebase-js-sdk.md)).
  The app already has the `signInWithCredential` path for account linking, so the change is one
  branch in `signInWithGoogle` and `linkAnonymousWithGoogle`. It also needs the app's signing
  fingerprints registered in the Firebase console *(from memory)*. Not built.
- Anonymous and email/password sign-in make no popup and should work unchanged *(from memory,
  untested)*.
- The same guide initialises auth on native with `indexedDBLocalPersistence` so "the user is
  still signed in the next time the app is started". The app uses `getAuth()`. Check on the
  phone whether a sign-in survives a force-stop.

### Two more things that break in the shell

- **Manage subscription.** `ManageSubscription.tsx` calls `/.netlify/functions/paddle-portal`.
  Inside the shell that is `https://localhost/...`, which does not exist. It needs the site's
  full URL, and the function would need to accept the shell's origin.
- **The pricing page.** Paddle's overlay inside the WebView is a store-policy problem before it
  is a technical one. See the next section.

## What store builds would need

### Google Play

- **Account.** "There is a US$25 one-time registration fee", with government ID
  ([link](https://support.google.com/googleplay/android-developer/answer/6112435?hl=en-GB)).
- **Closed test first.** A personal account created after 13 November 2023 needs "a minimum of
  12 testers" opted in "continuously for at least 14 days" before production access
  ([link](https://support.google.com/googleplay/android-developer/answer/14151465?hl=en-GB)).
  This is the longest lead time on the list. Twelve classmates would do it.
- **Target API.** From 31 Aug 2026, "New apps and app updates must target Android 16 (API level
  36) or higher" ([link](https://support.google.com/googleplay/android-developer/answer/11926878?hl=en-GB)).
  The generated project targets 36.
- **Signing.** Play App Signing holds the app key; you hold an upload key and must not lose it
  ([link](https://support.google.com/googleplay/android-developer/answer/9842756?hl=en-GB)).
- **Data safety form and a privacy policy link**, required even for an app that collects
  nothing ([link](https://support.google.com/googleplay/android-developer/answer/10787469?hl=en-GB)).
  `docs/STORE-DATA-DECLARATIONS.md` is the starting point and must be re-read first: it has been
  wrong before (see docs/CLAIMS.md, "Corrected").
- **Listing.** Screenshots, a description held to docs/CLAIMS.md, a content rating
  questionnaire, a permanent app id.

### Google Play and the Paddle subscription

This is the part that decides it. The rule:

- "Developers charging for app downloads from Google Play must use Google Play's billing system
  as the method of payment", and the list of what that covers includes "subscription services
  (such as fitness, game, dating, education, music, video...)".
- "Other than the conditions described in Section 3, Section 8 and Section 9, apps may not lead
  users to a payment method other than Google Play's billing system."
  ([Payments policy](https://support.google.com/googleplay/android-developer/answer/9858738?hl=en-GB))

So the pricing page as it stands, with Paddle's checkout inside the app, is not allowed on
Play. There are three routes that are:

1. **Consumption-only. No fee to Google.** "Google Play allows any app to be consumption-only,
   even if it is part of a paid service. For example, a user could log in when the app opens and
   access content paid for somewhere else." The condition: nothing "can be purchased from within
   the app". Plain words are permitted, a link is not: "developers may choose to provide
   additional information about purchasing options without direct links, including using
   language such as: 'You can purchase this book directly on our website'". And "Outside of your
   app, you are free to communicate with your users about alternative purchase options."
   ([Understanding the policy](https://support.google.com/googleplay/android-developer/answer/10281818?hl=en-GB))
   For LocusMSK: the Android app hides `/pricing`, and every locked panel says something like
   "Subscriptions are bought at locusmsk's website" with no link and no button.
2. **Billing choice programme. Link out to Paddle, pay Google 10%.** Since 30 June 2026 this is
   open to developers serving "users within the United Kingdom and the European Economic Area"
   ([Android Developers Blog, 24 Jun 2026](https://android-developers.googleblog.com/2026/06/play-expanded-billing.html)).
   It requires offering Google Play Billing alongside, integrating the billing choice APIs, and
   reporting "all authorised transactions from users within 24 hours"
   ([enrolment](https://support.google.com/googleplay/android-developer/answer/17161464?hl=en-GB)).
   Fee on auto-renewing subscriptions: "10% + 5% billing fee", the 5% applying only when the
   purchase goes through Google's billing
   ([service fees](https://support.google.com/googleplay/android-developer/answer/112622?hl=en-GB)).
   That means building Play Billing as well as Paddle, a second entitlement source, a reporting
   job, and 10% to Google on top of Paddle's own fee.
3. **Play Billing only.** 15% in total, and the Android app stops using Paddle.

Paddle's own mobile guidance describes linking out to a hosted checkout in the system browser,
and asserts the right to do so only for iOS apps in the United States; it says nothing about
Google Play or the UK ([Paddle](https://developer.paddle.com/get-started/how-paddle-works/mobile)).

### Apple

- **Account and tools.** "The Apple Developer Program is 99 USD per membership year"
  ([link](https://developer.apple.com/programs/whats-included/)). Capacitor 8 needs Xcode 26
  ([link](https://capacitorjs.com/docs/ios)), and Xcode needs a Mac *(from memory)*. There is no
  Mac in this project.
- **In-app purchase.** 3.1.1: "If you want to unlock features or functionality within your app,
  (by way of example: subscriptions ... access to premium content ...), you must use in-app
  purchase." 3.1.3: apps "cannot, within the app, encourage users to use a purchasing method
  other than in-app purchase, except for apps on the United States storefront".
  ([Guidelines](https://developer.apple.com/app-store/review/guidelines/))
- **No reader exemption.** 3.1.3(a) covers "magazines, newspapers, books, audio, music, and
  video". A study app is not on that list. The path that fits is 3.1.3(b), multiplatform
  services, which allows access to what was bought on the web "provided those items are also
  available as in-app purchases within the app". So iOS means building Apple's in-app purchase.
- **No UK link-out today.** Apple's external-link entitlement page does not mention the UK
  ([link](https://developer.apple.com/support/storekit-external-entitlement/)). The CMA opened a
  consultation on a steering requirement on 30 June 2026 and published responses on 14 August
  2026; it is a proposal, not a rule
  ([CMA case page](https://www.gov.uk/cma-cases/sms-investigation-into-apples-mobile-platform)).
- **Wrapper risk.** 4.2: "Your app should include features, content, and UI that elevate it
  beyond a repackaged website." A Capacitor shell around the PWA with one notification is close
  to that line.
- The service worker does not register on iOS (above), so offline there depends entirely on the
  files in the app bundle.

## Open risks

1. **Nothing has run on a device.** The Android project has never been compiled. The first
   Gradle build may fail for reasons not visible from here.
2. **327 MB of pictures in the APK.** Either accept it and check Play's size limits, or rework
   picture loading for the shell.
3. **Google sign-in needs replacing** in the shell. Students who signed up with Google on the
   web cannot sign in until it is.
4. **Play payments.** Shipping the app with `/pricing` reachable would breach the policy. The
   consumption-only route means the app can never sell, only serve.
5. **A second thing to release.** Every web deploy would need an APK build, a Play upload and a
   review, or the app falls behind the site. The "new version" prompt would need switching off.
6. **Reminder edge cases**: clock changes, a phone that kills background alarms, a student in
   several time zones. The plugin warns that with Doze "these notifications can only fire once
   per 9 minutes, per app" ([docs](https://capacitorjs.com/docs/apis/local-notifications));
   one a day is well inside that.
7. **The free-area choice lives in localStorage.** A reinstall resets it, and with it the one
   permitted change. That is true of the PWA too, but reinstalling an app is easier than
   clearing site data.
8. **The exact-alarm removal is untested.** The plugin's documentation says scheduled
   notifications "won't be exact" without the permission, which is the intent, but whether the
   plugin handles its absence cleanly needs the phone.

## Not looked at

- **Web push from the existing PWA.** It would give reminders with no store, no wrapper and no
  payment-policy question, at the cost of a server job to send them. It may be the cheaper way
  to get the one feature this trial is for. Not researched.
- **A Trusted Web Activity** (Play's route for listing a PWA as it is). Not researched. The
  payments policy applies to it the same way *(from memory)*.

## Recommendation

**Do the one-phone Android test. Do not start store work yet.**

The trial exists to get review reminders. Everything else a wrapper brings is cost: a second
release channel, a rewritten Google sign-in, a 327 MB download or a reworked picture loader,
and a payments policy that either stops the app selling (route 1) or takes 10 to 15% and a
second billing integration (routes 2 and 3). On iOS it also needs a Mac, Apple's in-app
purchase and a review that may reject a wrapper outright.

So, in order:

1. Install Android Studio and run the checklist above on one phone. Half a day. It tells you
   whether the reminder is worth having when it is real.
2. Before anything else native, spend an hour on whether web push can deliver the same
   reminder from the PWA you already have.
3. If reminders prove their worth and web push cannot do it: Android only, consumption-only
   (route 1), with the pricing page hidden in the app and subscriptions sold on the website.
   Start the 12-tester closed test early, because it is 14 days whatever else happens.
4. Leave iOS until there is revenue to justify the Mac, the fee and Apple's in-app purchase.

**To reject this:** if being in the stores matters for its own sake (discovery, or a course
lead who expects "an app"), route 1 on Android is still the cheapest way in, and the list under
"Open risks" is the work.
