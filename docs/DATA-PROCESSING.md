## 2. The controller question — read this before sending us your DPA

**We are a controller in our own right, not your processor.** We are not asking you to accept that; we are telling you what we believe the arrangement is, because the answer changes which paperwork is appropriate and a mislabelled agreement protects nobody.

The reasoning:

- **Students sign up individually and directly.** Nobody is enrolled by the university. An account is created by the student, with their own email address or Google account, under our terms.
- **We determine the purposes and means.** What is recorded, how the revision scheduling works, how long data is kept, what the interface shows — none of it is decided by, or on the instructions of, a university.
- **Joining a class is the student's own act, and reversible by them.** A student enters a join code; nobody can be added to a class without doing so. Leaving is one action on their account screen and takes effect immediately.
- **The university does not instruct us to process anything.** A module leader who owns a class receives a summary about students who chose to join it. That is a disclosure by us to a separate controller, not processing on their behalf.

**What follows.** A standard Article 28 controller-to-processor agreement does not describe this relationship, and we will not sign one that says we process personal data "only on the documented instructions of the controller" when in fact we do not. If your governance process requires a signed instrument, the right one is a **data sharing agreement between two controllers**, and we are happy to work from your template or supply one.

**Where this could change.** If a university ever licenses LocusMSK and directs us to process data for its own purposes — enrolling cohorts itself, dictating retention, requiring us to act on its instructions — we would be a processor for that activity and an Article 28 agreement would be correct. We would tell you, not quietly carry on.

## 3. What is processed

### Data subjects

Students aged 16 or over who create an account. Educators who create a class. No one else.

### Categories of personal data

| Category | Detail | Source |
|---|---|---|
| Account identity | Email address, display name | The student, at sign-up |
| Revision activity | Per answer: structure, question type, whether correct, the answer given, time taken, timestamp | Generated by use |
| Derived progress | Per-structure counters, per-day totals, mastery state | Computed from the above |
| Class membership | Which class a student has joined, if any | The student, by entering a join code |
| Technical data | IP address and standard connection data, handled by the providers in §5 | Automatic |

**No special category data.** LocusMSK is a study tool. It holds no health information about its users and asks for none. It is not a clinical system and holds no patient data.

**Anonymous use.** The app can be used without an account. A random identifier is stored on the device, no email is collected, and no class can be joined.

**No advertising, no tracking, no third-party analytics.** There is no advertising SDK, no tag manager and no analytics package in the application. This is verifiable in the source.

### Lawful bases

| Purpose | Basis |
|---|---|
| Providing the app: account, revision history, scheduling across devices | Contract (Art 6(1)(b)) — the terms accepted on use |
| Showing a student's summary to a class they joined | **Consent** (Art 6(1)(a)) — given by entering a join code, withdrawn by leaving the class |
| Keeping the service working: aggregate usage, error rates, which questions perform badly | Legitimate interests (Art 6(1)(f)) — never involves profiling an individual |

Consent is the basis for the educator-visibility feature specifically, and it meets the standard: freely given (the app is fully usable without joining a class), specific, informed (the join screen states what an educator sees before the code is accepted) and as easy to withdraw as to give.

## 4. What an educator can and cannot see

This is the processing universities scrutinise, and the one we have designed hardest. It has its own assessment in `DPIA-EDUCATOR-VISIBILITY.md`.

**A class owner can see, for students who joined their class:** name, overall accuracy, how recently they were active, and which structures the student gets wrong most often.

**A class owner cannot see:** individual answers, what the student selected instead of the right answer, the question-by-question record, or when individual answers were given.

**How that is enforced.** Not by the interface. The per-answer log (`attemptEvents`) carries **no** cohort-owner read permission in `firestore.rules`, and neither do a student's private subcollections. What an educator reads is a set of counters at `cohorts/{id}/studentStats`, summed on the student's own device before anything leaves their account. A class owner querying the answer log directly is refused by the database.

An earlier version of the rules did grant that access, and removing it (change `CR-031`, and a second grant found and removed on 18 September 2026 while preparing this pack) is what allows the privacy policy to make the promise in plain terms.

## 6. Retention and deletion

| | |
|---|---|
| While active | Account and revision data is kept while the account is in use |
| Inactivity | Deleted after **24 months of inactivity**, enforced monthly |
| On request | Immediate, self-service, complete |

**Self-service deletion works and is thorough.** "Delete my account" on the account screen removes the user profile, every subcollection under it, every answer event, the class summary an educator sees, and any role record — see `src/features/anatomy-revision/data/accountLifecycle.ts`. There is no waiting period and no need to ask us.

**How inactivity deletion is enforced.** `scripts/deleteDormantAccounts.ts`, run monthly, removes every account whose last recorded activity predates the cutoff — taking exactly what a student's own deletion takes. The retention period lives in one module that both the privacy policy and the script read, so the published promise and the code that keeps it cannot drift apart.

This was a genuine gap until 18 September 2026: the policy made the commitment and nothing implemented it. We found it while preparing this pack, recorded it as risk R2 in the DPIA, and closed it the same day. It is described here rather than quietly fixed because a supplier who only tells you about the problems you could have found yourself is not worth much.

## 8. Security measures

**Technical.**

- Authentication is Firebase Authentication (Google or email/password). We never see or store a password.
- All traffic is over TLS.
- Access control is enforced **server-side** in `firestore.rules`, not in the client. The rules are in the repository, reviewed as code, and are the security boundary — a modified client gets refused reads, not extra data.
- Each student's record is readable only by them, an administrator, and — for the profile fields only — the owner of a class they joined.
- The per-answer log is append-only: there is no update permission, so a record cannot be rewritten. Deletion is granted to its author alone, because erasure outranks an immutable log.
- Class membership is proved, not asserted: changing which class you are in requires the class's join code or an invitation addressed to your verified email, so knowing a class id is not enough to join it.
- Administrator access is read-only across users and cannot be self-granted.

**Organisational.**

- Single operator; access to production is limited to that one account.
- No credential, key or secret is held in the repository, and none is present in its history.
- Changes are version-controlled. A test suite (911 tests as at 20 September 2026) and a content validator cover the
  application, and are run before release **by the operator** — we have no continuous integration
  server, so this is a working practice rather than an automated gate, and we would rather say so
  than let the figure imply otherwise.
- Deployment refuses to publish a working tree that does not correspond to a commit on the shared remote.

## 9. Breach notification

Any personal data breach will be reported to the ICO within 72 hours of becoming aware of it where the threshold is met, and to affected institutions **without undue delay**, with what is known at the time rather than waiting for a complete picture.

We have not committed to a fixed number of hours for notifying institutions, because we would rather meet a duty we can keep at any hour of any week than quote a figure that sounds better. If your own policy requires a specific period, say so and we will agree one in the data sharing agreement.
